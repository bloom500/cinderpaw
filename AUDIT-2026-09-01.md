## 3. F1 — the cloud deadline bug (the important one)

On 2026-08-22 the cloud time-to-first-token deadline was raised 30s → 300s
in all three layers (Rust `crates/feral-core/src/perf_policy.rs`, sidecar
`FeralAgent/src/egress/perf-policy.ts`, frontend `frontend-react/src/lib/perfPolicy.ts`)
because reasoning models on OpenRouter were killed mid-thought.

**The total deadline was left at 120s.** The timers are independent:

- sidecar `deadlineController()` arms a total timer for `totalDeadlineMs`
  that is **never cleared** (`FeralAgent/src/egress/inference-providers.ts:1264`);
- Rust host: `if elapsed_ms >= policy.total_deadline_ms { abort }`
  (`src-tauri/src/commands/chat.rs:265`).

So at t=120s the total timer fires on **every** cloud request, 180 seconds
before the 300s TTFT timer could ever fire. Consequences:

1. The user-reported bug ("reasoning models killed before responding") was
   **not actually fixed** — a model that thinks for 130s is still killed,
   now with `[total_timeout]` instead of `[ttft_timeout]`.
2. The watchdog can now only ever report `total_timeout` on cloud — the
   TTFT trip and its user-facing copy are unreachable.
3. The per-token prefill scaling (4 ms/token, "capped at totalDeadlineMs")
   was clamped to 120s for cloud, so even the *scaled* TTFT never exceeded
   the old ceiling — the scaling was dead too.
4. `300_000 > 120_000` is a logically impossible deadline configuration
   (first-token budget larger than whole-request budget) — nothing in any
   layer asserts coherence.

**Fix applied:** cloud `totalDeadlineMs` 120_000 → **600_000 (10 min)** in
all three copies, with comments explaining why total must be ≥ the largest
scaled TTFT (300s base + prefill) and that 600s leaves 5 min of generation
after a worst-case prefill. Still env-overridable via
`FERAL_TOTAL_DEADLINE_MS`. A coherence assertion
(`total >= ttft` for both targets) was added to all three test suites so
this class of misconfiguration can't recur silently.

**Product note for Darius:** 10 min total is a judgment call, not derived
from data (see F5 — the data doesn't exist). If cloud reasoning turns
should fail faster, lower it — but keep it above 300s or the TTFT
protection is void again.

## 5. F4/F7 — invariant linter, fixed and its (now truthful) findings

`check-invariant-coverage.ts` is supposed to verify each hard invariant in
`docs/invariants.md` has all four pillars (Doc/Test/Runtime/Audit) by
scanning for `INVARIANT I<n>` markers. Two defects made it a no-op:

1. the heading regex required `—` in a form that never matched the actual
   file headings → 15 invariants parsed as zero → the summary read
   "HARD: 0/15 complete" regardless of reality (and report mode exits 0);
2. `SRC_DIRS` omitted `crates/feral-core/src` entirely — the Rust audit
   chain (`rsi/audit.rs`) and Rust RSI enforcement were invisible.

Both fixed. The **truthful** report now reads:

- **Audit pillar: 0/15.** No file classified as an audit path carries an
  `INVARIANT I*` marker — including `crates/feral-core/src/rsi/audit.rs`,
  which exists precisely to write invariants to the audit chain. The
  mechanism likely runs; the markers the four-pillar discipline requires
  are missing, so the gate cannot see it.
- **Test pillar missing:** I1, I2, I7, I9–I14. (I3–I6, I8, I15 have test
  markers.) I13/I14 are PENDING-by-design (data isolation, human approval
  gate) and should be excluded from strict failure rather than counted red.
- **Runtime pillar missing markers:** I9–I14 (SandboxBounds agent-
  immutability, personal fitness bound, fitness vector bound, provenance
  acyclicity) — enforcement may exist under other names; the linter only
  counts explicit IDs.

Recommendations: (a) wire `--strict` into the bun CI leg *after* (b) seeding
the audit markers in `rsi/audit.rs` and test markers for I1/I2/I7 —
otherwise CI goes red by construction; (c) make PENDING invariants a
separate report section, not failures.
