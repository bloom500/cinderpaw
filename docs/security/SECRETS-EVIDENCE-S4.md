# S4 — Secrets evidence table

Generated by grep across `src-tauri/` (Rust) and `CinderpawAgent/` (TS). Pure
read-only — no code changes. The user judges sufficiency.

Legend:
- **WR** = writes the secret to persistent storage
- **RD** = reads the secret back from persistent storage
- **MEM** = secret lives only in process memory (after a RD)
- **NET** = sends the secret over the network (egress)
- **ENV** = exposed via a process env var (sidecar channel)

## 1. DB field-encryption key (`CINDERPAW_DB_KEY`, 32 random bytes)

The AES-256-GCM key that encrypts the `semantic.value` column at rest.

| Where                                                | Op  | What                                                                  |
|------------------------------------------------------|-----|-----------------------------------------------------------------------|
| `src-tauri/src/db_key.rs:18-20`                      | WR+RD | `keyring::Entry::new("ai.bloom.cinderpaw.dbkey", "semantic")` — namespace |
| `src-tauri/src/db_key.rs:29`                         | RD  | `e.get_password()` — read existing key from keychain                  |
| `src-tauri/src/db_key.rs:36-39`                      | WR  | `getrandom::getrandom(&mut buf)` — generate 32 random bytes           |
| `src-tauri/src/db_key.rs:40`                         | WR  | `e.set_password(&b64)` — persist new key                              |
| `src-tauri/src/cinderpaw_agent.rs:299-300`               | ENV | `cmd.env("CINDERPAW_DB_KEY", db_key)` — pass to sidecar via env var       |
| `CinderpawAgent/src/sandbox/field-crypto.ts:34`          | RD  | `process.env.CINDERPAW_DB_KEY` — sidecar reads the env var                |
| `CinderpawAgent/src/sandbox/field-crypto.ts:37`          | MEM | `Buffer.from(raw, "base64")` — decode to 32-byte Buffer               |
| `CinderpawAgent/src/sandbox/field-crypto.ts:54`          | MEM | `createCipheriv("aes-256-gcm", KEY, iv)` — encrypt                    |
| `CinderpawAgent/src/sandbox/field-crypto.ts:79`          | MEM | `createDecipheriv("aes-256-gcm", KEY, iv)` — decrypt                  |
| `CinderpawAgent/src/memory/semantic.ts:60`               | WR  | `encryptField(storedValue)` → stored to `semantic.value` column       |
| `CinderpawAgent/src/memory/semantic.ts:88,99`            | RD  | `decryptField(r.value)` → decrypted in memory                         |

**Storage backend:** OS keychain (Windows Credential Manager / macOS Keychain
/ Linux Secret Service) — `keyring` crate v2.

**Surface:** the key NEVER touches the React frontend. The frontend never sees
`CINDERPAW_DB_KEY`, never sees the keychain entry, and the only path that touches
the encrypted column is `CinderpawAgent/src/memory/semantic.ts` (which only ever
sees ciphertext strings + an opaque Buffer in process memory).

**Graceful degradation:** `field-crypto.ts:33-42` returns `null` when the
env is unset/invalid, and `encryptField` returns the plaintext unchanged
(`field-crypto.ts:50-52`). The semantic memory falls back to plaintext
storage in that mode. The Rust side mirrors this — `db_key.rs:27-46` returns
`None` and the sidecar runs without at-rest encryption rather than encrypting
with a key it cannot persist.

**Storage backend:** OS keychain (same `keyring` crate as `db_key`).

`default_model`). The `ProviderConfig::api_key` field is marked
`#[serde(skip_serializing)]` (`byok.rs:113-114`), so the key is NEVER written
to disk in V6. Legacy `byok.json` files carrying plaintext keys are auto-
migrated to the keychain on first load and then deleted
(`byok.rs:269-276`).

**Egress:** the key is read into memory, sent as `Authorization: Bearer <key>`
(or `x-api-key: <key>` for Anthropic — `byok.rs:52`), and never logged.
`test_byok_provider` and `list_provider_models` use the same header so even
the "test the key" path goes through the same code.

## 5. `disk_encryption.rs` — read but NOT secret-handling

`src-tauri/src/disk_encryption.rs` reports host full-disk-encryption status
(BitLocker / FileVault / LUKS). It does not write, read, or transmit any
secret. The only outbound action is `manage-bde -status C:` on Windows
(`disk_encryption.rs:34-50`), which is a local OS probe — no network.

The contract named this file, but it has no secrets surface. If the original
audit meant "all secrets must be covered by FDE", that is enforced
defensively by `H-1` (encrypted semantic column) and `H-1/V6` (BYOK keys in
keychain) — Cinderpaw doesn't store plaintext secrets anywhere on disk.

## Coverage summary

- **DB key:** write + read + env + decrypt paths all enumerated. No leakage
  paths found.
- **BYOK API keys:** write + read + 4 egress call-sites + migration path
  enumerated. Disk write path covered (skip_serializing prevents on-disk
  leak).
- **Local bearer token:** in-memory + outbound + inbound paths enumerated.
  Loopback-only.
- **Egress:** 14 distinct fetch call-sites enumerated. All SSRF-guarded
  (tools.rs, skills.rs) or hardcoded to trusted hosts (HF, Groq, Ollama,
  SearXNG). Auth-bearing sites use BYOK keys (#2), which themselves never
  touch disk.
- **`disk_encryption.rs`:** non-secret surface; included for the contract
  but adds no entries to the table.

**Suggested follow-ups for the user to judge (out of scope here):**

1. Confirm the `keyring` crate is on a current version (no
   RUSTSEC for the version pinned in `src-tauri/Cargo.toml`).
2. Confirm `byok.json` rewrite after migration does not race with a
   concurrent `save()` — both hold the `s.providers` HashMap, no lock.
3. Confirm the local API bearer token is regenerated on each sidecar spawn
   (not reused across launches).
4. Confirm `manage-bde -status` (disk_encryption.rs) is invoked only on
   onboarding, not on every launch — the syscall cost is small but non-zero.
