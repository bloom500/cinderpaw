## Findings

All read in code; 2 and 3 were also run.

### L3 (code patches)

1. **`code-main` saturates after the first tiny green patch.** The score
   (`crates/cinderpaw-core/src/rsi/code_patch.rs:109`, `score_code_patch` at
   :118) is `60 * pass_rate + 15 * tsc + 15 * build + 10 * (1 - lines/200)`.
   A green one-line addition scores 99.95; the ratchet on `code-main`
   (`repo.rs:357`) is absolute and strictly greater, so nothing can beat it
   afterwards. Only a candidate that advanced reaches the approval queue
   (`CinderpawAgent/src/rsi/l3-code/code-rsi.ts:222`), so after that L3 stops
   sending patches without a word. The score also prefers the smallest
   harmless patch: a green 50-line patch scores 97.5 and loses to a one-liner.
   It measures "breaks nothing, is small", not "is better". `3531aa3` split
   the L1 and L3 lineages; this problem survived the split.
2. **Denylist gaps.** `isolation.ts:22` says the file is on the L3 patch
   denylist; it is not, in TS (`code-genome.ts:362`) or Rust
   (`code_patch.rs:35`). `validateCodePatch` run on 26 Sep ACCEPTS patches to
   `l3-code/isolation.ts` (the Docker cell), `l4-modules/module-host-client.ts`
   (runs the L4 wall, scrubs the env), `l4-modules/module-eval.ts` (L4 gate),
   `l2-adapt/lora-eval-gate.ts` (L2 gate) and `infra/bridge.ts` (the wire to
   the Rust ratchet). A human still approves every applied patch; the
   denylist exists so that click is not the only wall.

### L4 (modules)

3. **Generated module code runs on the host, not isolated.**
   `spawnModuleHost` (`l4-modules/module-host-client.ts`: wall at :81,
   `Bun.spawn` at :103, env = PATH + seed) is a plain Bun process: network
   and the user's files are reachable. The only barrier is the lexical wall
   (`module-wall.ts:40`), and this passes it (run 26 Sep, `{ ok: true }`):

   ```ts
   const g = globalThis;
   const net = g["fe" + "tch"];
   const env = g["pro" + "cess"]?.env;
   const F = (() => {}).constructor;
   export default { retrieve(p) { return F("return 1")(); } };
   ```

   The same spawn serves evaluation, which runs BEFORE the human approval
   (`dispatch.ts:479` `module_evaluate` → `rsi/sidecar.ts:319`), and the live
   seam after promotion (`seam-adapter.ts:122`). L3 moved into Docker for
   exactly this reason (Astra's audit, 12 Sep); L4 did not. Today's
   mitigation: evaluation only runs when the operator asks, and the proposer
   is local-only.

### L5 (governance)

4. **`frozen.l1` is read by nothing.** `cinderpaw governance freeze l1` is
   accepted and recorded (`governance-lifecycle.ts:474`), the fail-closed
   builtin sets it (`governance.ts:132`), and dream episodes keep evolving:
   nothing under `l1-config/`, `rsi/sidecar.ts` or `rsi/engine.ts` consults
   governance. `tests/l5-governance-fail-closed.e2e.test.ts:79` asserts the
   flag, not its effect.
5. Not in the plan, decision open: `approvals.l6Evolve` is read by nobody
   (`governanceCheck("l6_evolve")` has no caller; `meta-evolution.ts` reads
   `frozen.l6` itself, :474 and :567). L5 never proposes a policy itself;
   only the operator does (`governance_propose`), while `docs/brsi-spec.md`
   §5 says L5 auto-applies within bounds. Fix the doc or the code.

### L6 (meta)

L6 only moves when someone runs `cinderpaw meta evolve` (`dispatch.ts:194`);
nothing schedules it. So none of this acts by itself today, but whoever runs
it gets decisions made on noise.

6. **It scores accept rate, not improvement.** `metaFitness`
   (`meta-evolution.ts:252`) is `0.4 * accepts/rows + 0.4 * mean aggregate +
   0.2 * (1 - halt rate)`. Rows include every candidate, so fewer candidates
   per episode (a lower `dream_batch`, which L6 itself sets) raises the score
   with no improvement at all.
7. **"5 dream cycles" is 5 journal rows** (`MIN_META_CYCLES`, :197). One
   episode at the default `dream_batch` 40 writes up to 41 (a row per
   candidate plus the summary), so L6 can settle after a single episode.
8. **The baseline is never re-measured.** After a reject the old score stays
   the bar (:511), compared against later, unpaired windows in which ratchets
   are naturally rarer (the champion gets harder to beat): a drift toward
   rejecting everything.
9. **The window mixes layers.** L1 candidate rows (`contract-deps.ts:119`),
   L3 code rows (same writer), L4 module rows (`module-lifecycle.ts:457`) and
   the episode summaries share one journal, and `metaFitness` has no layer
   filter. L6 steers only L1.

## Plan (approved, in order)

### 1. L1 obeys `frozen.l1`

- The door: `RsiSidecar.start` (`rsi/sidecar.ts:393`). The UI's `rsi_start`
  and every Dream Cycle start pass through it. Refuse with
  `layerFrozen("l1")`'s reason, split like the "engine already running"
  branch above it: a UI start (`ackId`) gets an error event, a background
  start only a log line.
- Minimal scope: refuse new starts. A running episode ends within its budget;
  say so in the commit rather than adding a mid-episode stop.
- Test: a temp governance dir with `l1` frozen → start refused, no engine,
  no journal row; unfrozen → it starts. Check the test fails without the fix.

### 2. Close the denylist gaps

- Add to `code-genome.ts` and `code_patch.rs` together (the parity test
  `tests/rsi-code-patch-denylist-parity.test.ts` fails on drift): the five
  confirmed above, `isolation.ts`, `module-host-client.ts`, `module-eval.ts`,
  `lora-eval-gate.ts`, `bridge.ts`.
- Read each of these and add it if it decides or measures something:
  `module-host.ts`, `module-lifecycle.ts` (approval + promotion),
  `module-registry.ts` (repoints a seam), `seam-adapter.ts` (watchdog),
  `tier-loader.ts` (loads Tier 1/2), `fixtures.ts` (promotion partitions),
  `lora-eval-runner.ts`, `lora-registry.ts`.
- Test: `validateCodePatch` refuses each, in TS and in the Rust tests.
- Later, as its own decision: flip the denylist to an allowlist of what L3
  may patch, everything else protected by default. The list has already been
  missed three times (Astra 12 Sep, `5e3e31f`, this one).

### 3. L6: count episodes, L1 only, re-measure the baseline

- Evidence counts episodes: summary rows (`experimented === null`), so
  `MIN_META_CYCLES` means what its message says.
- Candidate rows only where `experimented.layer === "L1"`; L3/L4 rows out.
- Accepts per episode, not per row. Open question, recommend in the commit:
  per episode favours big batches, so the fair unit is main-score gained (or
  ratchets) per token spent. First check what `makeCycleSummary`
  (`l1-config/dream-cycle.ts`) carries.
- After a reject: revert and do NOT propose in the same call. The next
  `evolve()` measures the reverted champion over a fresh window (settles as
  `bootstrap`) and only then proposes. Costs one window per rejected
  generation and gives contemporaneous comparisons.
- Tests: `tests/rsi-meta-evolution.test.ts`: one 41-row episode is not enough
  evidence; L3/L4 rows are ignored; after a reject the next call re-measures.
  Keep the per-candidate fixture shape from `c32b661`.

### 4. L3: score relative to the base, not to the all-time best

- Measure the unpatched base in the same sandbox (same image, same steps) and
  let a candidate through when it is no worse than the base on passes/fails,
  tsc and build. Rust decides (TS never grades itself): hand Rust both
  measurement sets and score both there. Diff size stays a tiebreak, never a
  reason to prefer a no-op.
- Cache the base measurement per base commit + image hash: the base is the
  same for every candidate until an approved patch lands.
- Every candidate that clears the gate goes to the approval queue; cap the
  queue. Decide whether `code-main` stays a ratchet at all or only records.
- Files: `code_patch.rs` / `repo.rs`, `code-rsi.ts`, `code-leaves.ts`,
  `code-sandbox.ts`.
- Out of scope, write it down: nothing measures that a patch makes the agent
  better (that needs the L1 eval suite under the patched build).

### 5. L4 modules run inside the isolation backend

- Isolate in `spawnModuleHost`: evaluation and the live seam both spawn
  through it, so one change covers both.
- `IsolationBackend` (`isolation.ts:64`) only runs steps to completion; the
  module host is a long-lived JSON-lines process, so it needs an interactive
  variant (`docker run -i --rm --network none`, module dir mounted read-only,
  same limits). Same rule as L3: no backend → refuse, never fall back to the
  host.
- The live seam keeps one long-lived container per module; measure recall
  latency before and after.
- Keep the wall as a cheap first filter and stop calling it the boundary
  (docs in `module-wall.ts`, `module-host-client.ts`).
- Tests: unit tests with an injected exec; a live Docker test like L3's if
  the Linux runner has Docker.

## Architecture, in one line

The skeleton holds (immutable Rust scorer and ratchet, clamped bounds,
tighten-only policy, fail-closed loading, hash-chained journal and audit, one
contract FSM, human gates, Docker for L3). What does not hold is what it
measures: absolute scores stored without their context (model, suite, scorer
version, window), protection by a list of names, safety done per layer
instead of through one door, and empty post-deploy stages (`monitor` passes
everything for L1 and L3).
